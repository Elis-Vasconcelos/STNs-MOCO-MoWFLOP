## The two front variants

The reference front (which nodes are Pareto) and the ruler are built per wind
scenario (angle, wind speed). The two variants differ only in what else enters
that per-scenario front:

| folder | tags | originals front | sparse front |
|---|---|---|---|
| `noext/` | `x60noextnorm`, `g1.0noextrunnorm`, ... | our 6 executions of that scenario (MOEA/D and NSGA-II x p10/p50/p100) | same: our 6 executions |
| `ext/` | `x60norm`, `g1.0runnorm`, ... | + the real CEC (wflopcec26) runs with the same scenario: one twin per scenario (1 MOEA/D + 1 NSGA-II execution) | + sparse runs 10-29 laid out as CEC runs, only where their wind matches a run 0-9 scenario |

- **`noext` is the comparable set** (same rule and same amount of data on both
  sides). Use it for sparse vs original comparisons.
- **`ext` is Arthur's suggestion** (2026-10-04): the sparse runs 10-29 imitate
  the CEC runs. Each fake CEC run is the p10 execution of each algorithm only,
  because a real CEC run is one execution per algorithm. The rule is the same
  as for the originals but the amount is not: the originals get a twin for
  almost every scenario, the sparse instances only where the wind matches:
  ns506 runs 11, 16; ns507 25; ns508 15, 17, 19; ns509 27; ns510 13, 22;
  ns511 13; ns512 23; ns513 17, 20, 23, 29 (`inputs/prep_report.txt`).
- The STN graphs are the same in both variants (checked, below). Only
  Pareto labels and the metrics that depend on them change: `pareto`,
  `par_strength`, `n_end`, `path_par`, `path_par_reach`.

## Known limitations (same in both variants and both families)

- Pareto labels use an exact 6-decimal match against the pooled front, while
  the STN logger records only about 5-16% of a run's final archive, so
  `pareto`, `par_strength` and `path_par` partly reflect sampling.
- The aggregated (`norm`) front is a union of per-scenario fronts on the
  normalized scale, not one nondominated set (`runnorm` does not have this).
- The Tchebycheff function in the STN logger (and in MOEA/D's replacement) is
  unscaled, so the logged starting points favour the cheapest layouts.
- Runs launched in the same second share their starting population
  (time-based seed); they diverge by generation 50.
- Grid partitioning is slow on ns513 (185,054 candidate positions) because
  `geometry.estimate_candidate_spacing` computes a diagnostic by brute force
  (about 1 h per call on a shared core). The value is only reported in
  `reports/partition_summary_*.json`; it does not affect cells, nodes or
  metrics. To be fixed in a separate commit after this campaign.
